# Architecture Overview

## Components
1. **Orchestrator** (`orchestrator/`, C# console app): the agentic SDLC control
   plane.
   - `PipelineEngine.cs`: scheduling, gates, approvals, retries, fallback,
     rollback, re-planning, safe-stop.
   - `Stages.cs`: what each SDLC stage does and which gates it declares.
   - `Policies.cs`: security, compliance and change-control rules.
   - `CodebaseAnalyzer.cs` + `LineDiff.cs`: brownfield code reasoning and patches.
   - `TestRunner.cs`: real `dotnet test` execution + TRX parsing, and the static fallback.
   - `AuditLogger.cs`, `Metrics.cs`: observability.
   - `ConsoleApprover.cs`: the human in the loop.
2. **Orchestrator tests** (`orchestrator.Tests/`): the control-flow paths and
   policies, tested in isolation.
3. **Brownfield baseline** (`baseline/UrlShortener.Api/`): a frozen v1 of the
   service that the brownfield scenario analyses and patches.
4. **Generated artifacts** (`generated/`): the URL shortener product
   (`UrlShortener.Api` minimal API + `UrlShortener.Tests`). These are written
   *by* the pipeline; `audit.log` records how they came to exist.
5. **Docs** (`docs/`): `requirements.md`, `design.md`, `release-notes.md` and
   `brownfield/*` are generated by the pipeline; the rest are hand-written.

## Orchestration model
The engine is a **wave-based DAG scheduler with gates**:

```
                entry/exit gates on every stage; ◆ = human approval
requirements ──▶ design ──▶ ◆implementation ──┬──▶ testing ──┐
                   ▲                          │              ├──▶ ◆release
                   │                          └──▶ docs ─────┘       │
                   └──── re-plan (ReplanFrom) ◀── testing            │
                                testing ◀── rollback (CHG-002) ──────┘
```

- **Waves:** every stage whose dependencies have all succeeded runs in the
  same wave (`Task.WhenAll`). `testing` and `docs` run in parallel, and
  `release` synchronises on both.
- **Stage lifecycle:**
  `entry gate → approval (if required) → execute with bounded retries →
  fallback (if defined) → exit gate → Succeeded`. A stage's status is one of
  `Pending / AwaitingApproval / Running / Succeeded / Failed / Blocked /
  RolledBack / Rejected`.
- **Deferred resets:** rollbacks and re-plans requested during a wave are
  queued and applied only once the whole wave has finished, so a reset can't
  be overwritten by a sibling stage that is still running.

## Control flow features
| Requirement | Where it lives |
|---|---|
| Dependency graph with entry/exit gates | `StageDefinition.DependsOn`, `EntryGate`, `ExitGate`. Every stage has an exit gate on its output; implementation and release also have entry gates. Registering a stage before its dependency is rejected |
| Sequential + parallel paths with synchronisation | Wave scheduler in `PipelineEngine.RunAsync` |
| Cross-stage context & decision lineage | `PipelineContext` key/value store. Every `Record` is also written to `audit.log` as a `decision` event attributed to the stage that made it (via `AsyncLocal`) |
| Human approval checkpoints | `RequiresApproval` on `implementation` and `release`. The approver sees the policy warnings being accepted, and reviewer identity plus accepted warnings are logged |
| Bounded retries | `ExecuteWithRetriesAsync`: `MaxRetries` (default 2) with backoff |
| Fallback | `StageDefinition.Fallback`: Testing falls back from `dotnet test` to a static test inventory, marked `testing.degraded=true` |
| Rollback | A gate returns `RollbackTarget`, and `RollbackTo` resets the target and everything downstream (release → testing when there are too few tests) |
| Safe-stop | Rejection, a Block finding, a gate that throws (fails closed), or a failure with no fallback halts the run; exit code 1 |
| Policy guardrails (security / compliance / change control) | `Policies.cs`: SEC-001/002, CMP-001, CHG-001…005, plus stage-quality gates REQ/DES/TST/DOC/REL. See `docs/risks-and-validation.md` |
| Dynamic re-planning | `StageResult.ReplanFrom` → `RePlan` resets the stale stage and everything downstream, including stages that already succeeded (ambiguous scenario) |
| Audit-grade observability | `AuditLogger`: append-only JSONL, one line per event (policy, approval, start, retry, exception, fallback, rollback, replan, decision, outcome) |
| Reliability metrics | `MetricsTracker`: per-stage runs, retries, rollbacks, fallbacks and duration; success rate; incidents and MTTR; wall-clock latency split into automated time and human approval wait |
| Codebase reasoning (brownfield) | `CodebaseAnalyzer`: endpoint inventory, endpoint→store data flow, rule-based defect findings with file:line evidence, and impacted vs. unimpacted files |

## Key design decisions
- **In-process state machine over a workflow framework.** For a 2-3 day
  prototype, a hand-rolled scheduler is easier to reason about and to defend
  line by line than a heavier framework, and every control-flow path is unit-tested.
- **Gates are separate from stage work.** A stage *does* something, and its
  gates *judge* it. That keeps the policy set reviewable in one file
  (`Policies.cs`) and lets the same rule fire at different points: SEC-001 and
  CMP-001 run on implementation output, SEC-002 at release.
- **Recoverable problems roll back; unrecoverable ones block.** Too few tests
  can be fixed by re-running Testing, so it rolls back. Failing tests, an
  unverified security control, a stale design or an out-of-scope change
  can't be fixed by the pipeline itself, so they safe-stop for a human.
- **Degraded evidence is never treated as proof.** The fallback keeps the
  pipeline producing evidence when the test runner is down. Policy still
  refuses to ship a security control that no executed test has verified.
- **Stages write real files and run real tools.** The audit trail, test
  results and deliverables all come out of the same run, and nothing is
  hardcoded to look like it passed.
- **Brownfield is a patch, not a rewrite.** The existing code is checked out,
  only the changed files are written, and the diff is the reviewable change.
  Scope is enforced against the impact analysis (CHG-004), and the fix is
  verified by re-running the same analysis (CHG-005).
- **In-memory persistence for the API.** It keeps the prototype runnable with
  no external dependencies. The store sits behind `IUrlStore`, so swapping in
  EF Core/SQL is a contained change.
